# API List

Every planned API operation, what it receives (headers, path, query, body) and what it returns. **Draft.** The OpenAPI schema generated by drf-spectacular (`contracts/schema.yml`) is the source of truth; this page is the plan the schema is built from, and the one `PAGES.md` references. Conventions shared by all endpoints are in `CONTRACTS.md`; this page repeats only what you need to read an operation row.

Each operation has an **ID** such as `sales.create`. IDs are stable and are the names used in `PAGES.md`, in the task files, and as the `operationId` in the schema. Add new operations at the end of their group and keep the IDs.

## 1. How to read the tables

| Notation | Meaning |
|---|---|
| `*` after a name | required |
| `path:` `query:` `body:` `header:` | where the input goes |
| `a / b` | either a or b (or the enum values) |
| `{a, b}` | allowed values |
| `[x]` | list of x |
| (perm) | only included if the user has that permission |
| Money and quantity | decimal strings, for example `"125.50"` and `"1.250"` |
| Time | ISO 8601 UTC, for example `2026-11-15T09:30:00Z` |
| `list` output | `{ results: [...], next: cursor or null }` |

Milestones (M1 to M14) say when each group is built. Backend task IDs are in the group headings.

## 2. Common rules

### Request headers

| Header | When | Meaning |
|---|---|---|
| `Cookie` (session) | web, every request except public ones | Session token set at login. Sent by the browser through the Next.js proxy. |
| `Authorization: Bearer <token>` | native clients instead of the cookie | Same session token. |
| `X-CSRFToken` | cookie requests using POST, PUT, PATCH or DELETE | CSRF protection. Header name proposed; fixed in M1. |
| `Content-Type` | requests with a body | `application/json`, or `multipart/form-data` for uploads |
| `Accept-Language` | optional | `bn` or `en`; selects message language. Default: the shop's default language. |
| `X-Device-Id` | terminal endpoints only (`auth.device_check`, `auth.terminal_staff`, `auth.pin_login`) | Secret identifier of a registered register device |
| `X-Client-Type` | login endpoints only | `web` (default, token in cookie) or `native` (token also returned in the body) |
| `X-Request-ID` | optional | Echoed back; also appears in error bodies |

Response headers: `X-Request-ID` always. `Set-Cookie` on `auth.login`, `auth.pin_login` and `auth.context` (web).

### Rules that apply everywhere

- **Tenant.** Shop, branch and register come from the session context. Shop-scoped endpoints never take a `shop_id`. Only `platform.*` endpoints use shop IDs. Before a context is chosen, only the `auth.*` operations marked "any session" work.
- **Permission.** The "Perm" column is the permission code needed (section 3). `any` = any signed-in user with a context. `public` = no session needed.
- **Lists.** Query `limit` (default 50, max 200), `cursor`, `ordering` (field or `-field`) plus the filters shown. Master-data lists may use page numbers; the schema states which.
- **Standard resource operations** (section 4): `list` = `GET /x`, `create` = `POST /x` (201 with the object), `get` = `GET /x/{id}`, `update` = `PATCH /x/{id}` (partial), `delete` = `DELETE /x/{id}` (204; deactivates, never hard-deletes records that are referenced).
- **Idempotency.** `client_request_id*` (a UUID made by the client) is required on operations that move stock or money. Repeating it returns the original result (HTTP 200) instead of creating a duplicate. Operations with it: `sales.create`, `sales.complete`, `returns.create`, `goods_receipts.create`, `due_collections.create`, `supplier_payments.create`, `shifts.open`, `stock.opening`.
- **Approval.** Some actions need a manager. The client calls `approvals.managers` and `approvals.create` first, then sends the returned `approval_id` in the body of the real call. An approval is single-use, short-lived and tied to its action. Missing approval returns `APPROVAL_REQUIRED`.
- **Branch scope.** Data is limited to the branches the user may access. Lists and reports apply this automatically: a cashier sees their own shifts and sales, a manager their branch, an owner every branch of the shop (unless `branch_id` narrows it).
- **Errors.** One envelope (see `CONTRACTS.md`). Common errors on every operation: `AUTH_SESSION_ENDED` (401), `AUTH_CONTEXT_REQUIRED` (401), `PERMISSION_DENIED` (403), `VALIDATION_ERROR` (400, field messages in `details`), `NOT_FOUND` (404), `THROTTLED` (429). The Errors column lists only the extra ones.
- **Audit.** Writes to settings, prices, roles, members, voids, returns, adjustments and platform actions are recorded in `audit_logs` automatically.

## 5. Shared objects

Short shapes used in many responses. Full types come from the schema.

**Sale**: `{id, bill_no, status ({held, completed, voided, partially_returned, returned}), branch {id, name}, register {id, name}, shift_id, cashier {id, name}, customer {id, name} or null, lines [ {id, variant_id, name, name_bn, sku, unit {id, code}, quantity, unit_price, discount_amount, tax_rate_percent, tax_amount, line_total, batch {id, batch_no, expiry_date} or null} ], subtotal, discount_total, tax_total, service_charge, rounding_adjustment, grand_total, paid_total, change_given, due_amount, payments [ {id, method, amount, tendered, transaction_ref, verification_status} ], coupon_code, promotions [ {promotion_id, name, discount_amount} ], print_count, note, sold_at, voided_by, void_reason}`

**Shift**: `{id, branch, register, user {id, name}, status ({open, closed}), opening_cash, expected_cash (restricted), counted_cash, cash_difference, opened_at, closed_at}`

**Money fields** are strings with 2 decimals; **quantity fields** have 3 decimals; **percent fields** are decimal strings.
