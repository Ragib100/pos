# API Contracts

The agreement between backend and frontend. The **OpenAPI schema** generated by drf-spectacular and committed in `contracts/schema.yml` is the source of truth for every endpoint and type. This page holds the conventions that apply to all endpoints, the shared error format, and the open questions. The planned operations are listed in `API.md`, and the pages that call them in `PAGES.md`.

**Status: draft.** Conventions here are proposed starting points. The team finalizes them in M0 and M1 and records any change in `DECISIONS.md`.

## How the contract works

1. Before building an endpoint group, the backend task publishes its schema (request, response and error types) in a pull request.
2. The frontend generates its typed API client and a mock server from `contracts/schema.yml` and builds against the mock.
3. When the backend task is merged, the frontend switches to the real endpoints. The mock must match the schema exactly.
4. A contract change needs a heads-up to the other lane and a schema update in the same pull request. CI fails if the committed schema is out of date.

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1/`. JSON in and out, UTF-8 (Bangla text throughout). |
| Authentication | Opaque session token (D-020). Web: httpOnly cookie set through the Next.js proxy. Native: `Authorization: Bearer <token>`. |
| CSRF | Cookie-authenticated unsafe requests (POST, PUT, PATCH, DELETE) carry a CSRF token header. The exact header name is fixed in M1. |
| Tenant | Never sent by the client for shop-scoped data. The shop, branch and register come from the session. Only platform-admin endpoints take shop IDs. |
| IDs | UUID strings (server-generated UUIDv7). |
| Timestamps | ISO 8601 in UTC, for example `2026-11-15T09:30:00Z`. Display uses the shop's time zone. |
| Money and quantity | Decimal **strings**, for example `"125.50"` and `"1.250"`. Never floats. Percentages are decimal strings too. |
| Names | Fields that appear on receipts come as `name` and `name_bn`. |
| Language | `Accept-Language: bn` or `en` selects message language. |
| Pagination | Cursor pagination by default: `?limit=` and `?cursor=`, response `{ "results": [...], "next": "<cursor or null>" }`. Small master-data lists may use page numbers; the schema says which. |
| Filtering and order | django-filter query parameters, and `?ordering=field` or `?ordering=-field`. |
| Idempotency | Creating a sale takes `client_request_id`. Repeating it returns the original sale instead of creating another. |
| Versioning | Breaking changes get a new path version. Additive changes (new optional fields, new endpoints) do not. Frontend and backend deploy independently, so every change must work with the previous version of the other side; for an additive change, deploy the backend first. |

## 2. Error format

All errors use one envelope:

```json
{
  "error": {
    "code": "SHIFT_REQUIRED",
    "message": "Open a shift before selling.",
    "details": {},
    "request_id": "…"
  }
}
```

HTTP status: `400` validation, `401` not authenticated or session ended, `403` not allowed, `404` not found, `409` conflict, `422` business rule, `429` throttled.

Draft error codes (final list lives in the schema):

| Code | Meaning |
|---|---|
| `AUTH_INVALID_CREDENTIALS` | Wrong phone, email, password or PIN |
| `AUTH_LOCKED` | Account or PIN temporarily locked |
| `AUTH_SESSION_ENDED` | Session expired or revoked |
| `AUTH_CONTEXT_REQUIRED` | No shop, branch and register chosen yet |
| `PERMISSION_DENIED` | Role does not allow the action |
| `APPROVAL_REQUIRED` | A manager approval is needed first |
| `VALIDATION_ERROR` | Field-level problems in `details` |
| `NOT_FOUND` | Record does not exist for this shop |
| `LAST_OWNER` | Cannot remove or demote the last active owner |
| `SHIFT_REQUIRED` | No open shift for this user and register |
| `SHIFT_ALREADY_OPEN` | The user or the register already has an open shift |
| `OUT_OF_STOCK` | Not enough stock and the policy blocks the sale |
| `PAYMENT_NOT_COMPLETE` | Payments do not cover the total |
| `SALE_NOT_VOIDABLE` | The shift is closed or the sale is not completed |
| `RETURN_WINDOW_EXCEEDED` | The return time limit has passed |
| `CREDIT_LIMIT_EXCEEDED` | Customer credit limit would be exceeded |
| `COUPON_INVALID` | Coupon expired, used up or not applicable |
| `THROTTLED` | Too many attempts; retry later |

## 3. Shared types (draft)

Defined in the schema; listed here so both lanes use the same words.

| Type | Main fields |
|---|---|
| `Me` | user, memberships, current context (shop, branch, register, role, permissions) |
| `Context` | shop, branch, register |
| `Product` / `Variant` | names, SKU, barcodes, units, prices, tax rate, tracking flags, custom attributes |
| `StockLevel` | variant, branch, batch, quantity, average cost |
| `Sale` | bill number, status, lines, totals, payments, customer, shift |
| `Payment` | method, amount, tendered, reference, status |
| `Shift` | register, cashier, opening cash, expected, counted, difference, status |
| `ApprovalRequest` | action, entity, requester, approver |

## 4. Open contract questions

- Final CSRF header name and cookie names (decide in M1).
- Pagination style for each master-data list.
- Mock tooling for the frontend (generated from the schema).
- Payment states for pending card and MFS verification (see the resilience matrix, row 8).
